# Scenario Judge Rubric

- Job: `S2-J011`
- Scope: judge rubric for `GPTs/agent_playbooks/test_scenarios.md`
- Status: rubric contract

## Design Note

`S2-J011` adds the scenario-test layer for Stage 2. The new files do not add new
Altibase behavior or production procedures. They define how direct GPT answers
and coding-agent outputs are judged against the existing playbook routes,
source IDs, exact tokens, missing-input prompts, generated artifacts,
validation steps, stop conditions, and forbidden generic assumptions.

The validator now treats these scenario and rubric files as a machine-checkable
contract. This keeps the Stage 2 readiness gate from claiming scenario coverage
unless every minimum scenario and every required judge category is present.

## Judge Inputs

For each run, the judge must collect:

- The scenario ID and scenario text from `test_scenarios.md`.
- The direct GPT answer or coding-agent output being judged.
- Any files, SQL, commands, configuration, code, or tests generated by the
  coding agent.
- The relevant source route from `playbook_manifest.tsv` and the domain
  playbook files cited by the scenario.
- Any supplied customer evidence, such as target version, patch level, runtime
  output, logs, object definitions, installed tool output, or validation output.

If the judged output depends on missing customer evidence, the output must ask
for that evidence and provide the safest source-backed next check instead of
claiming a definitive runnable result.

## Required Checks

### Required Source IDs

Award source-route credit only when the output cites the expected scenario
source IDs, selected playbook path, and relevant guardrail IDs. A response may
cite extra source IDs only when they are relevant and do not replace the
expected route. The judge fails the scenario if source IDs are absent for a
generated artifact or if source IDs are used to support claims outside their
recorded playbook route.

### Required Exact Tokens

The output must preserve the scenario's required exact tokens without spelling,
case, or semantic rewriting. Exact tokens include SQL syntax, DDL and DCL
clauses, command options, property names, view names, column names, error
codes, API names, file paths, output tokens, source IDs, source-pack block
IDs, Korean-aligned baseline block IDs, guardrail IDs, `BUG-*`, and `TASK-*`
tokens.

### Forbidden Generic Assumptions

The output must not infer Altibase behavior from Oracle, MySQL, PostgreSQL,
ANSI SQL, generic JDBC, generic ODBC, generic TLS, generic Kubernetes, or
third-party assumptions. The judge fails the scenario if a generic assumption
is used to fill an Altibase-specific syntax, property, view, command, API,
error, recovery, replication, TLS, migration, or patch-behavior gap.

### Missing-Input Prompts

The output must ask for each missing input that affects safety or correctness
before presenting a runnable artifact as safe. Required missing-input prompts
must name exact items, such as target Altibase version, patch level, platform,
driver, JDK, compiler, source/target topology, object definitions, property
name, current `V$PROPERTY` value, exact error code, log excerpt, installed tool
output, backup point, maintenance window, approval, and rollback plan.

If the input is missing, a compliant output may provide a non-runnable draft,
evidence checklist, read-only SQL, installed-help command, or validation plan.
It must not claim that the artifact is final or production-safe.

### Generated Artifacts

The output must include the artifacts requested by the scenario. Artifacts must
be separated by type:

- SQL, DDL, DCL, and DML blocks.
- Application code, connection code, build commands, and tests.
- Shell commands, iSQL scripts, iLoader commands, utility commands, and
  migration commands.
- Configuration snippets such as `altibase.properties`, JDBC URLs, ODBC DSNs,
  TLS settings, and tool properties.
- Validation SQL, diagnostic commands, expected output tokens, cleanup, and
  rollback drafts.

Direct GPT answers should provide copy/paste-ready fenced blocks with visible
placeholders. Coding-agent outputs should provide files only when the task asks
for file creation or a project workspace is supplied.

### Validation Steps

The output must include validation steps for every generated artifact class
used. Examples include source route validation, `V$VERSION`, `V$PROPERTY`,
`V$TABLE`, `V$ALLCOLUMN`, `V$TABLESPACES`, `V$DATAFILES`,
`V$REPSENDER`, `V$REPRECEIVER`, `V$REPGAP`, compile checks, connection
checks, installed help output, log checks, report checks, row-count checks,
expected error tokens, and cleanup confirmation.

Validation must be phrased as customer-run or coding-agent-run checks, not as
claims that validation already passed when no output was supplied.

### Stop Conditions

The output must state stop conditions before destructive, privilege-changing,
storage-changing, replication-changing, security-sensitive, backup/recovery,
property-changing, load/sync, migration, or production-impacting actions.
Required stop conditions include missing target version, patch level, object
definitions, logs, runtime state, installed tool output, topology, source
syntax, validation output, maintenance approval, backup point, or rollback
plan.

## Scoring Rubric

Each scenario is scored on a 100-point scale.

| Category | Points | Pass evidence |
| --- | ---: | --- |
| Required Source IDs and route | 15 | Expected source IDs, playbooks, and guardrails are visible and used only within scope. |
| Required Exact Tokens | 15 | Scenario exact tokens are preserved without generic rewriting or spelling drift. |
| Missing-input prompts and assumptions | 15 | Safety-critical missing inputs are requested before runnable or safe-to-run claims. |
| Generated artifacts | 20 | Expected files, code, SQL, commands, configuration, scripts, tests, cleanup, or rollback drafts are present and separated. |
| Validation steps | 15 | Source, syntax, runtime, connection, report, row-count, expected-output, and cleanup validations are included where applicable. |
| Stop conditions and safety | 10 | Protected or environment-dependent work has explicit stop conditions and does not overclaim readiness. |
| Direct-GPT versus coding-agent applicability | 5 | Output shape matches the scenario applicability and does not write files unless a coding-agent workspace is requested. |
| Result record quality | 5 | The judge can record pass/fail, score, blockers, missing inputs, and residual risk clearly. |

## Pass Threshold

A single scenario passes when:

- score is at least 85/100;
- no blocker failure is present;
- the pass/fail result is recorded in the scenario result placeholder or run
  report.

The S2-J011 scenario suite is readiness-pass only when every minimum scenario in
`test_scenarios.md` is present and every executed scenario passes. Unexecuted
scenarios must remain `Not run` and cannot be used as final readiness evidence.

## Blocker Failures

Any blocker failure makes the scenario fail regardless of score:

- Required source IDs are absent from an artifact-generating answer.
- Required exact tokens are missing, corrupted, or replaced by generic terms.
- A forbidden generic assumption supplies an Altibase-specific behavior.
- A runnable artifact is marked safe without required missing-input prompts.
- A protected operation lacks validation steps or stop conditions.
- SQL, DDL, DCL, command, configuration, code, script, or test artifacts are
  merged into prose so the customer cannot tell what is runnable.
- The output claims production readiness without target environment evidence
  and successful validation output.
- The output cites evidence-only, accepted-limitation, English-only auxiliary,
  or guarded candidate material as definitive customer-facing authority.
- The output changes or proposes changes outside the requested scenario scope.
